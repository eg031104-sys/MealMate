# Smart shopping: sources, limitations and pricing

Investigated 23 October 2026. No retailer credentials, authenticated product feeds or live stock feeds are configured. The existing supermarket **location finder is unchanged**. A saved store is not evidence of catalogue access.

## Permitted sources and access

- Coles [website terms](https://www.coles.com.au/important-information/terms/website-terms-conditions), Woolworths [shopping terms](https://www.woolworths.com.au/shop/services/terms-and-conditions), ALDI [legal notice](https://www.aldi.com.au/legal-notice), IGA [online terms](https://www.igashop.com.au/terms): consumer websites/directories do not constitute a reusable product API grant for this app. No unofficial retailer endpoints, scraping, authentication bypass or reverse engineered mobile credentials are used. This investigation did not obtain an authorised API integration for any chain. IGA stores independently set prices, which can differ from the online basket.
- [WhichGrocer API terms](https://www.whichgrocer.com/developers/terms) permit application display of returned product information, including images when supplied. Calls must be from a backend using an issued key; client keys are prohibited. Its terms say the provider does not warrant retailer authorisation, coverage is retailer-level, and cache rights can be withdrawn. **Not connected**: there is no account/key, purchased plan, secure backend or verified data. Future adoption requires terms/coverage review, server-side credentials and any provider subscription/hosting costs. No costs were incurred here.
- [Open Food Facts API](https://openfoodfacts.github.io/openfoodfacts-server/api/) and [licences](https://openfoodfacts.github.io/openfoodfacts-server/api/tutorials/license-be-on-the-legal-side/): community product database (ODbL), individual contents (DbCL), photos (CC BY-SA; attribution links shown). Selected records retain barcode, original name, brand, reported quantity, source link and timestamps; no synthetic branded products are bundled. Source fields are tagged `community`, separate from household price overrides. Database/image rights must be retained in any redistributed derived collection.

### Implemented community adapter

“Find real product records” explicitly searches Open Food Facts for the ingredient, Australia and selected chain (Coles, Woolworths, ALDI or IGA). It validates the response, deduplicates barcodes, checks chain/country tags, requires a compatible measurable pack and conservatively matches the ingredient phrase. It rejects unrelated prepared foods such as milk chocolate, rice crackers and pasta sauce. Users review and choose a match; only their chosen record is saved offline. An ambiguous match is not automatically imported into household data.

The official docs state that v2/v3 do **not** support full-text search; the adapter therefore uses the documented legacy `/cgi/search.pl` keyword endpoint rather than silently sending an ignored `search_terms` filter to v2. This is a maintenance limitation; the adapter interface allows a future supported/licensed replacement. Search is button-driven, never search-as-you-type, at most once per seven seconds, with a 12-second timeout, five-minute failure cooldown and 24-hour session result cache. No immediate automatic retries. User-selected records persist in IndexedDB and JSON backups. Returned photo URLs must be HTTPS on `images.openfoodfacts.org`; thumbnails lazy-load and failures use a placeholder. Remote photos are not added to the service-worker cache.

**Live verification remains unavailable**: the development network proxy rejected a direct request to `world.openfoodfacts.org` with HTTP 403 CONNECT. This is not evidence of a browser CORS failure or a successful API response. Adapter behaviour is tested using explicitly synthetic fixtures. The shipped browser request can still fail due to endpoint changes, CORS, network restrictions or provider load; errors name the provider and leave generic/manual workflows usable. No successful live chain product search, catalogue price or stock integration is claimed.

A community `stores_tags` value means a contributor associated the product with that retailer at some time. It does not confirm retailer listing today, local range, a current price, a special or stock. Availability remains unknown. The adapter does not return prices. Public reads use no private key; no paid API or backend is required for this experimental directory adapter. A future proxy would need a maintained service, caching, provider-compliant application identification/rate limits and appropriate hosting; none is required for the local estimate/manual workflow.

## Pricing and recommendations

The generic ingredient/required quantity always remains visible. Product identity and price provenance are separate. The existing trusted-provider gate remains empty: importing a record cannot self-certify an authorised catalogue price.

Resolution is: explicit user price override (always respected); valid configured catalogue price; previous configured catalogue quote with observation date; generic ingredient-type allowance; unknown. UI labels are Catalogue price, Previous price, Estimated price, User price and Price unknown. Existing legacy demonstration records retain their original provenance in storage; their display is treated as an estimate, not live data. Untrusted imported quotes are never used as verified prices.

`product-estimates.ts` contains broad **engineering allowances**, not a sourced retailer price survey or a current catalogue. Typical Australian purchase units include 200 g tomato paste, 500 g meat, 1 kg rice, 1 L milk and a dozen eggs. For example the generic tomato-paste allowance is approximately $3 per 200 g, without a brand or claimed supermarket association. Known product packages without a price use the same type allowance scaled to the actual pack. Allowances round to 50 cents and show `~`; they cannot distinguish brand premiums. Unknown types, incompatible units, prepared food and ambiguous stock/sauce forms remain unknown rather than receiving an arbitrary universal price. These allowances need household calibration using the editable package price. No branded catalogue listings were invented.

Balanced is the default. Budget emphasises total package outlay; Balanced weighs suitability, unit cost, actual basket outlay and surplus; Premium gives suitability more weight. There is no inferred brand-quality database: Premium is not “buy the most expensive”, and sparse alternatives intentionally do not invent tiers. Explicit saved product selections override ranking for that ingredient/store until changed or reported unavailable. Generic opt-out and package-specific price overrides persist per store and ingredient.

Required quantities aggregate all active meals first. Quantified, unexpired stock and purchases reduce outstanding requirements exactly once. Pack counts round up with floating-point tolerance. Unknown pantry quantities are not deducted as known stock: they remain in “Check your pantry” and the budget clearly flags the excluded uncertain costs. Unmeasured seasonings retain the existing partial-total notice. Actual purchases remain in the weekly cost even after the plan changes; entered actual prices are preserved. Predicted pack surplus is shown as potential waste and is **not** inserted into pantry inventory before purchase confirmation. No weight/volume conversions without ingredient-specific evidence were added.

Budget totals update through the existing shared shopping calculation whenever meals, portions, substitutions, product choices, pantry or overrides change. Estimated entry counts and missing/uncertain prices are disclosed. Totals remain planning targets, not checkout guarantees.

## Data safety and testing

The existing IndexedDB database, version 3, household store and state key are unchanged. Optional product metadata and optional `v3.shopping` are additive. Old V3 snapshots read with Balanced defaults without rewriting old records. No IndexedDB/localStorage clearing, deletion or reset was added. Existing recipes, archived flags, finder query/results, store assignments, history, purchases and pantry are retained; the backup schema validates the additional fields.

Tests cover provider validation/deduplication/absence of fabricated records, pack parsing, ranking, estimates, prices/overrides, pantry deductions, surplus/purchases, persisted data, user interactions and all existing planner/finder regressions. The scheduling panel is portalled to the document body with a viewport-width bottom sheet at <=600 px, accessible close/Escape/focus handling, and weekday controls only for fixed repeats. DOM tests exercise 320/360/390/430 px viewport settings and check the viewport-based CSS contract. jsdom does not compute visual geometry; physical Android appearance and external photo/API delivery still require device testing.
